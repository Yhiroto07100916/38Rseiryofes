# お知らせプッシュ通知機能 仕様書

- 対象リポジトリ: `Yhiroto07100916/38Rseiryofes`
- 対象ブランチ: `feature/web-push-notifications`
- 基準ブランチ: `main`
- 状態: 実装中（コード追加済み・環境設定と実機検証待ち）
- 作成日: 2026-11-05

## 1. 概要

38Rサイトに新しいお知らせが追加されたとき、通知登録を完了しているスマートフォンへWeb Push通知を送信する。

通知はユーザーアカウントごとに出し分けず、38Rサイトに通知登録されているすべての端末へ同じ内容を一斉送信する。

## 2. 対応環境

- iPhone・Androidの両方を対象とする。
- 38Rサイトをホーム画面に追加した状態で利用する。
- iPhoneはWeb Pushに対応するiOS/iPadOS 16.4以降のホーム画面Webアプリを対象とする。
- AndroidはWeb Pushに対応するブラウザ・端末を対象とする。
- 本番環境ではHTTPSを必須とする。localhostは開発時の例外とする。

## 3. 通知対象・アカウントとの関係

- 通知対象は、OS・ブラウザで通知が許可され、かつ38Rサイト側でPush Subscriptionの登録が完了している全端末とする。
- OSの通知許可だけではサーバーは送信先を知ることができないため、サイト側の登録操作も必要とする。
- ユーザーID、学籍番号、権限、クラス、ログイン状態による配信先の絞り込みは行わない。
- Push SubscriptionにユーザーIDを紐付けない。
- ログアウトしても端末の通知登録を維持し、通知を送信する。
- 端末が複数登録されている場合も、登録済み端末をすべて送信対象とする。ユーザー単位の端末管理機能は設けない。

## 4. 通知を送信する条件

| 操作 | 通知 |
| --- | --- |
| お知らせの新規作成 | 送信する |
| お知らせの編集 | 送信しない |
| お知らせの削除 | 送信しない |

- お知らせ本体と関連データの保存が完了した後に通知処理を開始する。
- お知らせの作成APIが失敗した場合は通知を送らない。
- 通知送信の失敗によって、保存済みのお知らせを取り消したり、作成APIを失敗扱いにしたりしない。
- 初回送信はお知らせ保存直後に開始する。

## 5. 通知の表示内容・動作

- 通知タイトル: お知らせのタイトル。
- 通知本文: お知らせ本文の先頭50文字。50文字を超える場合は末尾に「…」を付けて省略する。
- 通知元の表示名: 38Rサイト。
- 通知をタップしたとき: 該当するお知らせ詳細ページ（`/news/{newsId}`）を開く。
- 同じお知らせに由来する通知を識別できるよう、通知に一意な識別子（tag等）を設定する。

## 6. 通知の登録・解除（設定画面）

### 6.1 登録

- サイト内の設定画面に「通知を有効にする」操作を設ける。
- ページを開いただけ、またはログインしただけではOSの許可を要求しない。
- ユーザーがボタンを押したときに通知許可状態を確認する。
- 許可が未決定の場合はブラウザ・OSの許可ダイアログを表示する。
- 許可された場合はService WorkerのPush Subscriptionを取得し、Worker API経由でD1に登録する。
- すでに登録済みの場合は二重登録しない。
- 許可が拒否されている場合は登録せず、スマートフォン側の設定で許可を変更する必要があることを画面に案内する。

### 6.2 解除

- 設定画面に「通知を無効にする」操作を設ける。
- 解除操作ではブラウザ側のPush Subscriptionを解除し、Worker API経由でD1の対応する登録情報を削除する。
- サイト側の登録解除はOS全体の通知許可を取り消す操作ではない。その違いを画面上で説明する。
- 登録状態（登録済み・未登録・許可が必要・利用不可・処理中・エラー）を視覚的に表示する。

### 6.3 設定画面の配置

- リポジトリには独立した一般設定ページが現時点で見当たらない。
- 実装時の配置先は既存のマイページ（`/me`）への通知設定セクション追加を第一候補とする。ただし、実装開始前に画面配置を確定する。

## 7. 登録情報の保存

- D1に端末単位のPush Subscriptionを保存する。
- 保存対象はWeb Push送信に必要なendpoint、p256dh、auth等とする。
- ユーザーIDなどのアカウント識別情報は保存しない。
- endpointの重複登録を防ぐ一意制約を設ける。
- Push Subscriptionは送信先情報として機密性を持つため、一般ユーザー向けAPIで一覧取得・表示しない。
- VAPID秘密鍵はCloudflare Worker Secret等の秘密情報として管理し、Gitリポジトリにコミットしない。公開鍵のみクライアントに提供する。

## 8. 重複防止・送信履歴

- お知らせIDとPush Subscription IDの組み合わせで送信ジョブを一意にする。
- D1の一意制約等により、同一のお知らせ・同一端末に対する送信ジョブの二重作成を防止する。
- 送信処理の再実行で成功済みジョブを再送しない。
- Push Serviceの2xx応答は送信要求の受理を意味し、端末画面への表示完了を保証するものではない。
- ネットワーク障害など応答が不明確な場合、ユーザーに見える通知の完全なExactly-once（厳密な一度だけの配信）は保証できない。通知tagによる表示上の重複抑制も併用する。

## 9. 失敗時の再送・登録情報の削除

### 9.1 再送

初回送信に失敗した場合、一時的なエラーに限り再送する。

| 試行 | 実行タイミング |
| --- | --- |
| 初回 | お知らせ保存直後 |
| 1回目の再送 | 初回失敗から1分後 |
| 2回目の再送 | 1回目の再送失敗から5分後 |
| 3回目の再送 | 2回目の再送失敗から15分後 |

- 最大試行回数は初回を含めて4回。
- 再送時刻をD1に保存し、Workerの定期実行（Cron Trigger等）で期限到来済みジョブを処理する。
- Workerのリクエスト終了後も再送予定が失われない永続的な仕組みを用いる。単なるメモリ上のタイマーやリクエスト内の待機だけに依存しない。
- Cloudflareの定期実行は毎分を基本候補とするため、実際の再送時刻には実行スケジュールによる遅延があり得る。

### 9.2 エラー分類

| Push Service等の結果 | 対応 |
| --- | --- |
| 2xx | 送信要求を受理。成功として扱い登録情報を維持 |
| 404 / 410 | Subscriptionが無効。該当登録情報を即時削除し、その端末へのジョブを終了 |
| 429 | 一時的な送信制限。再送 |
| 5xx / ネットワークエラー | 一時的な障害として再送 |
| 401 / 403 | VAPID鍵・サーバー設定等の問題を疑い、端末登録情報を削除しない。運用ログに記録して調査対象とする |
| その他 | レスポンス内容に応じて恒久的エラーか一時的エラーかを分類し、誤削除を避ける |

### 9.3 ブラウザ側での状態確認

- 設定画面を開いたときにNotification.permissionとPush Subscriptionの状態を確認する。
- permissionがdenied、またはPush Subscriptionが存在しないことを確認した場合、対応するサーバー側登録情報を削除する。
- permissionがdefaultの場合は、ユーザーがまだ選択していない状態として扱い、勝手に許可要求を出さない。
- OS側で許可が取り消された瞬間にサーバーが必ず検知できるわけではない。次回サイト利用時または送信時に検知する。

## 10. 想定するシステム構成

- フロントエンド: 既存Nuxt 4 / Vue / TypeScript / Vuetify。
- PWA: 既存の`@vite-pwa/nuxt`を維持し、既存のWorkbox Service Workerと競合しないよう、`/push/`スコープに専用Service Workerを登録する。
- API: 既存Cloudflare WorkerにPush Subscription登録・解除APIと送信処理を追加する。
- DB: Cloudflare D1にSubscriptionと通知ジョブを管理するテーブルを追加する。
- 送信: VAPIDを利用したWeb Push。`@pushforge/builder` 2.0.5を使用し、Web Crypto APIとfetchでCloudflare Workersから送信する。
- 再送: D1の`push_notification_deliveries`をCloudflare Workerの毎分Cron Triggerで処理する。ローカルでも手動でscheduled handlerを呼び出せる。
- 既存のお知らせ作成処理（`POST /api/news`）と連携し、新規作成時だけ通知ジョブを作成する。

## 11. セキュリティ・運用要件

- Subscription情報を一般ユーザーに返さない。
- 登録・解除APIは既存の認証・CORS・入力検証の方針に従う。登録情報自体はアカウントに紐付けない。
- VAPID秘密鍵や認証情報をソースコード・Git履歴に含めない。
- ログにendpoint、auth、p256dh等の機密値を出力しない。
- 通知送信失敗や設定不備を調査できるよう、機密情報を除いた構造化ログを残す。
- 通知送信の失敗が、お知らせ作成の成功・失敗を左右しないようにする。
- 本番環境のSecret登録・Workerデプロイ・本番D1マイグレーションは、別途明示的な確認を得てから行う。

## 12. 受け入れ条件

1. iPhone（対応OS、ホーム画面追加済み）とAndroidの対応ブラウザで通知登録できる。
2. 設定画面から通知の登録状態を確認できる。
3. 設定画面から通知を解除できる。
4. 通知登録済みの全端末に、同じ新規お知らせの通知が送信される。
5. ユーザーID、権限、ログイン状態による配信先の絞り込みがない。
6. ログアウト後も登録済み端末には通知が送信される。
7. お知らせの編集・削除では通知されない。
8. 通知タイトル・本文が仕様どおりで、本文は先頭50文字に制限される。
9. 通知をタップすると該当のお知らせ詳細が開く。
10. 同一のお知らせ・同一端末の通知ジョブが重複作成されない。
11. 一時的な失敗は規定の間隔・回数で再送される。
12. 404・410等で無効と判断したSubscriptionは即時削除される。
13. OS側の許可が拒否されている、またはSubscriptionがない端末は登録状態が適切に整理される。
14. 通知送信に失敗しても、お知らせ自体は正常に保存される。
15. 既存のお知らせ閲覧・作成・編集・削除、ログイン、他機能に回帰がない。
16. ビルド・型チェック・関連テストの結果と、未検証事項が明確に報告される。
